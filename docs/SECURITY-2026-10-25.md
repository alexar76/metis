# Host execution, request signing and outbound HTTP, 2026-10-25

The built-in Python interpreter has no operating-system filesystem isolation.
A temporary working directory, subprocess, scrubbed environment and AST screen
do not provide that boundary. A harmless canary demonstrated private-import
access to host file APIs through an allowed module.

Host Python execution is now disabled by default. Production deployments and
HTTP/WebSocket request contexts always refuse it, including streaming responses
and spawned request tasks. An explicit `METIS_UNSAFE_LOCAL_CODE=1` opt-in is only
for trusted private development; it never overrides the public/production gate.
`enable_code_interpreter` now defaults to `false`. Public untrusted execution
requires a separate service with real operating-system isolation; no such backend
is claimed by this change. The private-import screen and runtime environment
allowlist are additional hygiene for the private opt-in, not isolation claims.

When request signing is enabled, a missing HMAC secret refuses both client signing
and server invocation instead of silently accepting an unsigned request. Existing
signed payloads keep the same canonical format. Worker request limits are checked
while reading the body rather than after buffering the entire request.

The safe HTTP helpers connect to the public IP that was actually checked and
preserve the original HTTP Host and TLS server identity. Every redirect is pinned
and checked again. Embedded credentials and non-public connection targets are
refused. Cross-origin redirects discard credential/custom headers and cookies;
307/308 redirects cannot forward a POST body to another origin. HTTPS certificate
verification remains enabled. Tests use mock transports, including DNS rebinding
and redirect credential probes, and perform no live external requests.
